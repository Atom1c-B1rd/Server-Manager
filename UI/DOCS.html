Documentación de Server Manager

Guía de uso y referencia técnica para crear, configurar, ejecutar y entender los servidores que administra esta aplicación.

Server Manager es una aplicación local. La interfaz se abre en http://localhost:3000; los servidores que creás usan sus propios puertos.

1. Qué es y cómo está organizado

Server Manager permite definir varios servidores en un solo proceso de administración. Cada servidor tiene un protocolo, puerto, handlers y configuración propios. La interfaz web se comunica con el proceso Go mediante WebSocket y envía operaciones para crear, editar, iniciar, detener y consultar servidores.

Interfaz (UI)

Permite administrar los servidores, editar rutas y handlers, ver logs y guardar ajustes.

Manager

Coordina las instancias en ejecución, selecciona el motor según el protocolo y controla su ciclo de vida.

Motores de protocolo

Implementan HTTP, WebSocket, TCP y UDP. Cada motor recibe la configuración de su servidor.

Runtime de handlers

Evalúa código Go de usuario con Yaegi, un intérprete de Go, para cargar funciones definidas desde la interfaz.

El código de los handlers se interpreta en tiempo de ejecución; no se crea un ejecutable independiente por cada handler. Las dependencias externas que necesite un servidor se preparan antes de iniciarlo.

2. Inicio rápido

  1. Pulsá Nuevo server.
  2. Elegí un nombre, protocolo y puerto. El puerto debe estar libre y dentro del rango 1–65535.
  3. Guardá la configuración. El servidor guardado puede seguir detenido: guardar no equivale a iniciar.
  4. Seleccioná el servidor en la lista lateral para abrir su panel de administración.
  5. Configurá sus rutas (si corresponde) y handlers. Revisá el código inicial y adaptalo a tu protocolo.
  6. Pulsá Iniciar y revisá el estado y los logs.
  7. Probá el endpoint o conectá un cliente usando la dirección, puerto y formato de mensaje adecuados.
El puerto 3000 está reservado para la propia interfaz de Server Manager; no lo uses para uno de los servidores administrados.

3. Servidores y estados

  • Crear: genera una configuración para el servidor.
  • Guardar: persiste los cambios de configuración. Según el ajuste editado, puede ser necesario reiniciar el servidor para que el proceso activo use la nueva configuración.
  • Iniciar: carga la configuración, prepara dependencias pendientes, crea el motor correspondiente y comienza a escuchar en el puerto configurado.
  • Detener: detiene la instancia en ejecución; la configuración guardada no se elimina.
  • Logs: muestran eventos de inicio y detención, conexiones, mensajes y errores que registre el motor.
  • Inicio automático: si está activado, Server Manager intenta iniciar ese servidor cuando arranca la aplicación.

Los servidores son independientes en su configuración y puerto. No pueden escuchar simultáneamente en la misma combinación de dirección, puerto y protocolo si el sistema operativo no permite compartirla.

4. Servidor HTTP

HTTP se usa para endpoints de petición/respuesta, por ejemplo una API REST. Cada handler HTTP se asocia a un método y una ruta.

CampoSignificadoEjemplo
MétodoMétodo HTTP que activa el handler.GET, POST
RutaPath de la petición./health, /users
NombreIdentificador descriptivo del handler.HealthCheck
CódigoFunción Go compatible con una de las firmas soportadas.Ejemplo abajo

Firmas aceptadas por el motor:

func(c echo.Context) error

func(w http.ResponseWriter, r *http.Request)

Ejemplo de handler Echo para responder texto:

func HealthCheck(c echo.Context) error {
    return c.String(200, "ok")
}

El motor registra cada petición en los logs con método, ruta, código HTTP y latencia. Si no hay handlers configurados, el motor registra una respuesta básica en /.

5. Servidor WebSocket

En WebSocket hay dos conceptos distintos: rutas y handlers de mensajes.

Rutas WebSocket

Definen el path HTTP en el que se acepta el handshake y se establece la conexión. Ejemplos: /chat o /game. El cliente debe conectarse a la ruta correcta, por ejemplo ws://localhost:8081/chat.

Handlers WebSocket

Se eligen por el tipo del mensaje recibido y pueden asociarse a una ruta concreta. Así, el mismo tipo de mensaje puede manejarse de forma diferente en dos rutas distintas.

De forma predeterminada, el tipo del mensaje se obtiene del campo JSON type y el payload del campo data. El campo de tipo se puede cambiar en Formato de mensajes.

{"type":"chat.send","data":{"text":"Hola"}}

Firma esperada por los handlers WebSocket:

func HandleChat(conn *websocket.Conn, msgType int, payload []byte) error

conn es la conexión activa; msgType es el tipo de frame WebSocket original y payload contiene los bytes del campo data cuando existe, o el mensaje completo si no se extrajo ese campo. La función también puede definirse sin valor de retorno.

Los logs del motor incluyen la ruta y su ID, el tipo de mensaje y su contenido cuando corresponde, además de los eventos de conexión y desconexión. Evitá enviar secretos en mensajes que queden registrados.

6. Servidor TCP

TCP es un flujo de bytes: no conserva límites de mensajes por sí solo. En esta implementación, cada mensaje debe terminar con un salto de línea (\n) y contener un objeto JSON.

{"type":"login","data":{"username":"admin"}}

El campo type identifica el handler y data se entrega como bytes JSON. Se puede configurar otro nombre de campo para el tipo.

func HandleLogin(conn net.Conn, payload []byte) {
    var input struct {
        Username string `json:"username"`
    }
    if err := json.Unmarshal(payload, &input); err != nil {
        return
    }
    // Procesar input y responder mediante conn.
}

El cliente debe agregar \n al final de cada mensaje JSON. El handler recibe la conexión TCP para poder responder al cliente.

7. Servidor UDP

UDP trabaja con datagramas independientes y no garantiza entrega ni orden. El formato de este servidor es una cabecera de texto con el tipo, seguida de un salto de línea y el payload binario.

login\n<bytes del payload>

El texto anterior al primer \n se compara con el campo Path / tipo del handler. Todo lo que viene después se pasa como []byte. UDP no interpreta el payload como JSON automáticamente.

func HandlePacket(conn *net.UDPConn, addr *net.UDPAddr, payload []byte) {
    // Procesar payload y, si corresponde, responder:
    // conn.WriteToUDP(respuesta, addr)
}

El tamaño máximo teórico de un datagrama UDP es 65.507 bytes en IPv4, aunque en redes reales los datagramas grandes pueden fragmentarse o fallar. Preferí paquetes pequeños.

8. Handlers y formato del código

Un handler es una función Go que el motor carga y ejecuta cuando recibe una petición, conexión o mensaje que coincide con su configuración. El nombre de la función debe coincidir con la función que el runtime intenta resolver para ese handler.

  • Path / tipo: en HTTP es el path; en TCP, UDP y WebSocket representa el tipo del mensaje. En WebSocket la ruta de conexión se configura por separado.
  • Código: contiene la función handler.
  • Dependencias: paquetes externos requeridos por el código. Deben estar disponibles para el runtime antes de iniciar el servidor.
  • Formato de mensajes: en TCP y WebSocket, el campo JSON usado para reconocer el tipo de mensaje; el valor inicial es type.

Imports comunes como encoding/json y fmt forman parte del entorno inicial. El conjunto exacto de funciones y tipos disponibles depende del protocolo y de las dependencias configuradas. Para cada protocolo, respetá la firma documentada en su sección.

9. Código global del servidor

El editor de código global está pensado para declaraciones compartidas por varios handlers del mismo servidor: tipos, funciones auxiliares y variables globales. Usalo para evitar repetir la misma lógica en cada handler.

type LoginRequest struct {
    Username string `json:"username"`
}

func isEmpty(value string) bool {
    return strings.TrimSpace(value) == ""
}

El código global no sustituye la función de entrada de cada handler: cada handler necesita su propia función con la firma que requiere el motor. Mantené las declaraciones globales compatibles con el intérprete y con los imports disponibles.

10. Ajustes avanzados

Variables de entorno

Permiten configurar valores que el código puede leer mediante os.Getenv("NOMBRE"). Son útiles para opciones de ejecución; no publiques sus valores en logs.

Conexiones a bases de datos

Configurá un nombre, un driver compilado en la aplicación y un DSN. Los handlers pueden usar la conexión mediante el SDK del proyecto, por ejemplo sdk.DB("main") si la conexión se llama main. El DSN puede contener credenciales; guardalo con cuidado.

Dependencias externas

Agregá el path del paquete Go y una versión. Server Manager intenta instalar/preparar las dependencias antes de arrancar. Si falla, revisá el mensaje de error y la conectividad con el repositorio del paquete.

Inicio automático

Activalo solo para los servidores que quieras que intenten arrancar cada vez que se inicia Server Manager.

11. Cómo se selecciona un handler

  1. El motor recibe una petición o mensaje.
  2. Extrae el método y la ruta en HTTP, o el tipo del mensaje en TCP, UDP y WebSocket.
  3. Busca primero un handler con coincidencia exacta.
  4. Si no hay coincidencia exacta, busca un handler de tipo *, que funciona como fallback.
  5. Si no hay handler aplicable, TCP y UDP conservan una respuesta Echo predeterminada. El comportamiento de HTTP depende de las rutas registradas; WebSocket no ejecuta un handler de tipo que no coincida.
En WebSocket, el handler debe coincidir tanto con el tipo de mensaje como con la ruta a la que pertenece. Un handler sin ruta asociada se trata como compatible con todas las rutas, para mantener compatibilidad con configuraciones antiguas.

13. Problemas frecuentes

El servidor no inicia

  • Comprobá que el puerto no esté ocupado y sea válido.
  • Revisá los logs del servidor y el error que devuelve la interfaz.
  • Verificá que el handler exista y use la firma correcta.
  • Si el error menciona una dependencia, revisá el path, versión y acceso a internet para instalarla.

El handler no se ejecuta

  • Confirmá el método y path para HTTP.
  • Para TCP, asegurate de enviar JSON completo terminado en \n.
  • Para WebSocket, verificá la URL de conexión, el ID de ruta elegido para el handler y el valor del campo de tipo.
  • Para UDP, enviá tipo\n seguido del payload; no envíes un objeto JSON esperando que se extraiga el tipo automáticamente.
  • Usá * como handler fallback cuando tenga sentido.

El servidor inicia pero el código no responde

Revisá que la función tenga el nombre y la firma esperados, que valide el payload y que escriba la respuesta usando la conexión o el contexto recibido. Los handlers HTTP deben devolver un error o respuesta según su firma; los handlers TCP/WebSocket/UDP deben implementar explícitamente la respuesta cuando corresponda.
